# ADR 006 — Build-time master key with `xtask flash` auto-revert

**Status:** Accepted

## Context

Umbra's chain of trust binds three artefacts together with a single
secret value, the **master key**:

- the Secure-side firmware binary (the boot image and the kernel
  baked into `umbra-<mcu>-boot`),
- the enclave blobs delivered to NS flash or external XSPI,
- the supporting host-side tooling that signs the enclaves before
  flashing.

If any of the three holds a different master key, the chained
measurement at enclave load aborts with `MeasurementMismatch`. The
device boots; the enclaves do not run. This is intentional — a
mismatch is the visible signature that the chain of trust has been
broken.

The constraint is operational. A clean production deployment requires
the same key everywhere. A local development cycle requires the
freedom to test with a known key, rotate it, and confirm rotation
behaviour. Both flows have to share one mechanism, or the developer
ends up bypassing whichever mechanism is in their way.

The temptation in this situation is to make the master key a runtime
secret stored in OTP fuses or in a TrustZone-protected region. Two
reasons it does not fit Umbra's current scope:

1. **Cross-platform parity**. L552, L562 and N657 expose three
   different secure-storage primitives (RDP option bytes, OTFDEC
   region, DHUK + HUK derivation through CRYP1). The same key in
   three different containers means three different bring-up
   procedures, each with its own failure modes.
2. **The audit chain we actually care about** is between the source
   tree and the deployed binary. A developer auditing a release
   needs to verify "this firmware image was built against this
   master key value". A runtime secret defeats reproducibility of
   that check.

## Decision

The master key is a **build-time constant** committed to the source
tree at three locations:

- `src/hardware/platform/stm32l552/boot/src/master_key.rs` (L552/L562
  Secure-side constant);
- `src/hardware/platform/stm32n657/boot/src/master_key.rs` (N657
  Secure-side constant);
- `tools/master_key.bin` (host-side signing input).

All three are generated by `tools/gen_key.py` from a single
authoritative value. The Secure-side files are `#[doc(hidden)]`
`pub const MASTER_KEY: [u8; 32]` arrays; the host-side file is the
raw 32-byte binary form consumed by the signing tooling.

`cargo xtask flash` runs an **auto-revert step** after every flash
session that restores the three files to their committed state. The
xtask body documents and enumerates them:

```
src/hardware/platform/stm32l552/boot/src/master_key.rs
src/hardware/platform/stm32n657/boot/src/master_key.rs
tools/master_key.bin
```

This makes the recurring development pattern safe:

1. The developer runs `cargo xtask flash <platform>`.
2. The xtask flow regenerates the three files from a session-specific
   master key (set, by default, to the committed value).
3. The flash step runs end-to-end with consistent key material across
   firmware + enclaves + tooling.
4. The auto-revert restores the three files so that an `git status`
   immediately after the flash session is clean.

Any change to the master key value is therefore an **explicit
PR-level event**, not a side effect of running a flash command. The
reviewer can audit master-key churn by grepping git history for
modifications to those three paths.

## Alternatives considered

### Alternative A — Master key in OTP fuses, derived at runtime

Burn the key into MCU OTP and derive working subkeys at boot via the
silicon's KDF.

- **Pro**: keeps the secret off the source tree entirely. A leaked
  source repo does not leak the production key.
- **Con**: three target MCUs offer three different OTP / DHUK /
  RDP-protected-storage primitives. Implementing each one is its own
  bring-up effort and is not the scope of the current trust chain.
- **Con**: an auditor cannot verify "this firmware was built against
  this master key" by reading the repo. The link between source and
  deployed binary now requires HW access.
- **Con**: developers lose the ability to test key rotation paths in
  a tight loop because every test requires a new OTP burn.

**Deferred** — this is the right destination for a production
release. It is not the right shape for the current development
phase, where the chained-measurement logic itself is still evolving
and needs to be testable without HW-side ceremony.

### Alternative B — Master key in an environment variable, never on disk

The build reads `UMBRA_MASTER_KEY` from the environment on every
invocation. The Secure-side constant is generated at build time and
discarded.

- **Pro**: nothing key-shaped on disk; the secret lives only in the
  developer's shell history (and `~/.zsh_history`).
- **Con**: a Secure-side `pub const MASTER_KEY: [u8; 32]` is still
  baked into the binary by the linker. The disk artefact moves from
  the source tree to the `target/` directory; nothing is gained
  except an audit blind spot.
- **Con**: shell history is not better than git for this — it is
  worse, because the rotation event is not reviewed.
- **Con**: a developer who forgets to set the variable produces a
  build with a zero key, which silently corrupts every enclave they
  flash.

**Rejected** — moves the problem rather than solving it, and
introduces a failure mode (zero key) that has no recovery path.

### Alternative C — Build-time constant, no auto-revert

Same source-tree commitment as Decision, but no `xtask flash`
revert step.

- **Pro**: trivially simpler tooling.
- **Con**: every flash session leaves the three files dirty in
  `git status`. A developer who runs `git commit -a` after a flash
  picks up the residue.
- **Con**: a CI run that flashes a board (smoke test) and then
  commits artifacts (regression goldens) picks up the residue
  silently.
- **Con**: a developer who notices the dirty files and reverts them
  manually may revert *other* legitimate changes by mistake.

**Rejected** — the residue is a footgun whose cost grows with every
contributor.

### Alternative D — Move `master_key.rs` outside the source tree (gitignored)

Keep the file at the same path but gitignore it; generate it during
build only.

- **Pro**: the secret never enters git history.
- **Con**: `cargo build` on a fresh checkout fails because the
  Secure-side constant is missing. The developer has to know to run
  the generator first.
- **Con**: same audit blind spot as Alternative B — there is no
  record of which key was used for which build.

**Rejected** — broken first-checkout experience, and no audit gain
for the trust chain we actually care about.

## Consequences

### Positive

1. **Fresh-checkout builds work** because the master key is
   committed. No "did you remember to run the generator" step.
2. **Audit trail is in git**. Reviewing master-key changes is a
   `git log -p src/hardware/platform/*/boot/src/master_key.rs`
   command.
3. **The dirty-residue footgun is closed** by the `xtask flash`
   auto-revert. A flash session has no `git status` after-effects.
4. **The reviewer rule is mechanical**. Any diff touching the
   three master-key paths is rejected unless the PR is explicitly
   about master-key rotation.

### Negative

1. **The secret is in the repo**. A leaked source-tree leak the
   key. Production deployments that need true key secrecy must
   migrate to Alternative A (OTP-backed) before exposure.
2. **The auto-revert is `xtask`-specific**. A developer who runs
   the underlying programmer commands by hand (bypassing the
   xtask flow) does not get the revert. The recurring instruction
   to use `cargo xtask flash` exists in part to keep this property.
3. **Rotation is an explicit ceremony**. Bumping the key requires
   running the generator, committing the three files, and shipping
   the new firmware everywhere the chained measurement is
   anchored. There is no graceful key-rotation path because the
   chain of trust is, by construction, anchored to one value at a
   time.
