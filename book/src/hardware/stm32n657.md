# STM32N657 — NUCLEO-N657X0-Q

## Board Overview

The NUCLEO-N657X0-Q hosts an STM32N657X0 — a Cortex-M55 (ARMv8.1-M)
with TrustZone-M, hardware crypto, an integrated NPU (ST Neural-ART
Accelerator), and **no internal flash**. The MCU boots from external
XSPI2 via the on-board MX25UM51245G (512 Mb) NOR. Umbra runs as the
first-stage bootloader (FSBL) loaded by the Boot ROM into AXISRAM2.

## Key Characteristics

| Feature | Detail |
|---|---|
| MCU | STM32N657X0H3Q |
| Core | Cortex-M55, 800 MHz (CPU) / 400 MHz (AXI) / 200 MHz (HCLK) |
| Internal flash | **None** — FSBL lives in external XSPI2 NOR |
| SRAM | ~4.2 MB total (FLEXRAM, AXISRAM1–6, AHBSRAM1–2, plus 256 KB ITCM and 256 KB DTCM) |
| External flash | MX25UM51245G 64 MB / 512 Mb XSPI2 (memory-mapped at `0x70000000`) |
| HW AES | CRYP1 (AES-128, 14 cycles/block) — wired via `AesHardware` (ECB + native CTR); SAES preserved for future DHUK-wrap key-isolation |
| HW HMAC | HASH peripheral (SHA-1/224/256/384/512, HMAC); chained measurement runs in HW (~9 s for 11 MB) |
| External flash decryption | MCE1–MCE4 (currently passthrough on this board — see boot crate's `oracle.rs`) |
| NPU | ST Neural-ART, 900 MHz (clocked via PLL3 + IC6) |
| Debug UART | USART1 (PE5 TX / PE6 RX, AF7) via ST-Link VCP, **115200 baud** |
| LEDs | PG0 (green), PG8 (blue), PG10 (red) |
| Boot jumper | JP2 — Dev-Boot (2-3) for flashing, Flash-Boot (1-2) for run |
| Enclave storage | XSPI2 (header at `0x70090000`) |
| Block loading | CPU copy via memory-mapped XSPI2 read (MCE2 in passthrough) |

## UART Connection

The ST-Link provides a Virtual COM Port. No additional wiring needed.

- **Serial device** (macOS): `/dev/cu.usbmodem*`
- **Serial device** (Linux): `/dev/ttyACM0`
- **Baud rate**: 115200

## IDAU Aliasing

The N6 uses a different aliasing scheme from STM32L5: **the top nibble
encodes security state**.

| Top nibble | Security | Example |
|---|---|---|
| `0x0`, `0x2`, `0x4` | Non-Secure | `0x24000000` AXISRAM1 NS view |
| `0x1`, `0x3`, `0x5` | Secure / NSC | `0x34000000` AXISRAM1 Secure view |

SAU can re-classify NS regions in the even-nibble alias range. Secure
code always uses the odd-nibble alias.

## Memory Firewall (RIF)

The N6 replaces L5's GTZC with the RIF family:

| Block | Purpose | Key registers |
|---|---|---|
| RISAF1..23 | Per-memory access control (start/end addr, S/NS, R/W, CID) | RISAF`x`->CFGR, REGCFGR, BASEREG, ENDREG |
| RIFSC | Per-peripheral CID-aware enable | SECCFGR`x`, PRIVCFGR`x`, RCFGLOCKR |
| RIMC | Bus master CID tagging (DMA, NPU) | RIMC_MASTERCFG_*, RIMC_ATTR |
| IAC | Central illegal-access reporting | IAC_ISR, IAC_IER |

Umbra programs these in `PlatformBoot::init_security`. The bring-up
landmine to watch for: the IDAU "AXISRAM1 view" at `0x34000000` is
split across **RISAF7** (FLEXRAM, offsets < 0x64000) and **RISAF2**
(proper AXISRAM1, offsets ≥ 0x64000). Configuring only RISAF2 leaves
a hole.

## Flash Workflow

1. Set JP2 = **Dev-Boot** (2-3).
2. Plug the board in (CN1, ST-Link USB).
3. Build:
   ```bash
   export MCU_VARIANT=stm32n657
   source ./settings.sh
   ./rebuild_all.sh
   ```
4. Flash:
   ```bash
   tools/flash_n657.sh
   ```
5. Set JP2 = **Flash-Boot** (1-2) and reset.

`flash_n657.sh` writes:
- FSBL signed image at XSPI2 `0x70000000`
- Host bin at XSPI2 `0x70080000`
- (Object-detection demo) model bytecode and `network_data.xSPI2.bin`
  further up

```
[UMBRASecureBoot] Secure Boot started
[UMBRASecureBoot] AES KAT (HW): 3ad77bb40d7a3660a89ecaf32466ef97 PASS
[UMBRASecureBoot] CTR KAT (HW): 874d6191b620e3261bef6864990db6ce 9806f66b7970fdff8617187bb9fffdff PASS
[UMBRASecureBoot] AEAD surface: OK (placeholder)
[UMBRASecureBoot] Kernel Initialized
[UMBRASecureBoot] Jumping to Non-Secure World
[USER] Hello Non-Secure World!

```

The two KAT lines validate the CRYP1 hardware path at boot before the
engine is installed into the kernel:

- `AES KAT (HW)` — NIST SP800-38A F.1.1 ECB-AES128 Vector 1 (validates
  key load + ECB single-block encrypt).
- `CTR KAT (HW)` — NIST SP800-38A F.5.1 Vectors 1+2 (validates
  ALGOMODE=0x6 native CTR + HW counter increment between blocks).

Both must PASS or the boot panics. The `AEAD surface:` line confirms
the (currently placeholder) AES-GCM API surface compiles — see
[Crypto Architecture](#crypto-architecture) below.

## Crypto Architecture

The N657 crypto stack lives in [`src/hardware/platform/stm32n657/drivers`](https://github.com/HiSA-Team/umbra/tree/main/src/hardware/platform/stm32n657/drivers/src):

| Driver | Role |
|---|---|
| `cryp.rs` | CRYP1 register-level driver: ECB single-block, CTR streaming. Used on the production hot path. |
| `saes.rs` | SAES1 register-level driver: DHUK-wraps the enclave key and shares it to CRYP over the `SAES → CRYP` key bus at boot, so the key never sits in CPU-readable memory (see below). |
| `hash.rs` | HASH peripheral: SHA-256 / HMAC-SHA256 for chained measurement and key derivation. |
| `aes.rs` | `AesEngine` + `Aead` traits and the `AesHardware` composite that fans out into `cryp.rs` / `saes.rs`. Also keeps `AesEmulated` (T-table SW AES) as a fallback. |

### `AesEngine` trait

`init` configures CRYP for the DHUK-shared key — there is **no software
key load**; the key arrives over the `SAES → CRYP` bus at boot (see
below). `encrypt_block` / `decrypt_block` operate on single 16-byte
blocks (ECB), and `ctr_xform` does AES-128-CTR with a caller-provided
16-byte initial counter.

`AesEmulated` provides a T-table software AES-128 (~4 KB lookup tables
in .bss; ~8× faster than the byte-wise path on Cortex-M55).

`AesHardware` overrides `ctr_xform` to switch CRYP1 from ECB to native
CTR (ALGOMODE=0x6, IV loaded into `CRYP_IV0LR..IV1RR`). The peripheral
generates the keystream, XORs it with input, and increments IV1RR per
block — no manual loop in software.

### `Aead` trait

API surface for Authenticated Encryption with Associated Data — typed
seal/open with associated `KEY_SIZE`, `NONCE_SIZE`, `TAG_SIZE` consts
(defaults: 16/12/16, matching AES-128-GCM). Non-object-safe by design
(monomorphization keeps the embedded vtable cost at zero).

The current `AesHardware` impl returns `Err(AeadError::NotYetImplemented)`
from `seal`/`open` — a placeholder that will be filled in once CRYP1
GCM (ALGOMODE=0x8, RM0486 §49.4.13 four-phase init→header→payload→
final) is wired.

### DHUK shared-key delivery

The enclave AES key is delivered to CRYP over the `SAES → CRYP`
shared-key bus (RM0486 §48.4.15), so it never sits in a CPU-readable
field. At boot the key is wrapped via SAES under the device
**DHUK** (Derived Hardware-Unique Key, `KEYSEL=DHUK`), the wrapped blob
is kept in VBAT-retained backup SRAM (provision-if-absent, re-wrapped if
the key rotates), and SAES unwraps and shares it straight into CRYP —
`AesHardware::init` writes no key registers. A known-answer test at boot
confirms the shared key decrypts correctly, and the boot fails closed if
CRYP does not report a valid key.

The wrap/share procedure follows the STM32Cube HAL exactly (data flows
through `SAES_DINR`/`DOUTR` with `KMOD=SHARED`, a two-phase
key-derivation-then-decrypt unwrap, and the key fed most-significant-byte
first). On the BSEC-open Nucleo the DHUK is the silicon default, so this
delivers *isolation* (the key leaves no CPU-visible copy) rather than
*confidentiality* against an attacker who can read backup SRAM — full
confidentiality needs the irreversible OTP close (see below).

## Root of trust

On STM32N6 Umbra runs as the signed FSBL and layers several
root-of-trust hardenings. All of them stay **reversible on the
development board** — no OTP fuse is burned and debug stays enabled — so
each can be exercised without committing the part:

| Hardening | What it does | On the open board |
|---|---|---|
| **HDPL isolation** | The FSBL raises the Hide-Protection Level (HDPL1 → HDPL2) as its last Secure action before the Non-Secure handoff, so the HDPL1-derived DHUK is not recoverable by later stages. HDPL clears on power-on reset. | **Demonstrated** — the level transition is observable and the enclave still runs at HDPL2. |
| **Dual-FSBL fail-safe** | The signed image is flashed to both Boot-ROM slots (offset `0x0` and `0x40000`, per UM3234); the ROM falls back to image 2 when image 1 fails to load. | **Demonstrated** — corrupting image 1's header still boots (fallback triggers on structural failure, not only signature). |
| **Enclave anti-rollback (version bind)** | Gated by the `enclave_version_bind` feature. Rejects a stale, legitimately-signed enclave version — see [Enclave anti-rollback](#enclave-anti-rollback) below. | **Validated on HW** — a v2 enclave boots, a stale v1 image is rejected. |
| **ECDSA-P256 signing** | The FSBL is emitted as a signed STM32 v2.3 image with an anti-rollback version field, replacing the unsigned dev header. | **Pipeline validated** — a real signature is produced and the image boots; Boot-ROM *enforcement* needs the close. |

`UMBRA_FSBL_VERSION` feeds the signed-image anti-rollback field (`-iv`,
Boot-ROM-enforced only post-close). `UMBRA_VERSION_BIND` /
`UMBRA_AUTHOR_ID` / `UMBRA_ENCLAVE_VERSION` drive the enclave-side
anti-rollback above — a separate, already-enforced control that needs no
OTP. Signature and key-confidentiality *enforcement* for the FSBL image
itself are gated on the irreversible OTP `secure_boot` close, which is
intentionally out of scope for the open development board.

## Debug

Boot ROM holds the core until authentication and copy are done, so a
clean SWD reset is not possible. Attach without reset:

```bash
openocd -f openocd_scripts/stm32n6x.cfg
arm-none-eabi-gdb path/to/boot \
    -ex 'target extended-remote :3333'
```

For NPU work, the activations live in AXISRAM5/6 — those pages are
power-gated by default and `init_clocks` opens them as part of the
NPU bring-up (`G.1.a.3`).

## Enclave anti-rollback

Umbra can refuse an older, legitimately-signed enclave version after an
update, against a **remote/software** attacker. The mechanism is gated behind
the `enclave_version_bind` cargo feature (default OFF — the legacy
chained-measurement finalize is byte-identical when the feature is off), paired
with the offline tool's `UMBRA_VERSION_BIND=1` gate.

- **Version derived, never stored in clear.** The block measurement is
  version-independent; the version is bound by a trailing fold
  `header.hmac = HMAC(BM, "umbra-encver-v1" || author_id || version)` applied by
  `tools/protect_enclave.py::version_tag`. There is no clear-text version field
  to tamper. The kernel recomputes `BM`, then **searches** candidate versions
  (`kernel::key_storage_server::version_search::search_version`) starting at its
  stored floor; the candidate that reproduces `header.hmac` is the authenticated
  version. `BM` is `MASTER_KEY`-derived, so `header.hmac` is unforgeable for
  attacker code.
- **Search-from-floor IS the rollback check.** A version below the floor is
  below the search start, so it can never match — rollback is structurally
  unrepresentable. The floor is a per-`author_id` monotonic high-water-mark in
  the **TAMP backup registers** (`drivers::tamp_store`, `TAMP_BKPxR`), bumped
  only after a version is derived. These persist across a system reset AND a
  reflash — HW-verified 2026-06-30 (the increment-only `TAMP_COUNT1R` counted
  0→1→2 across plain resets, `TAMP_SR`/`TAMP_CR1` = 0, i.e. no tamper). The 8 KB
  BKPSRAM is *not* used: it does not retain across reset on the open Nucleo
  (`PWR_BDCR2.BKPRBSEN` covers only Standby/VBAT). Windows: `SEARCH_WINDOW` = 256
  (max version jump per update when provisioned); `COLD_WINDOW` = 1024 (scan when
  the floor is 0).
- **`author_id` is a build constant** (`UMBRA_AUTHOR_ID`, emitted by `build.rs`),
  not a host field. Anti-rollback is only as trustworthy as the author signing
  identity; a compromised key voids it. Multi-author provisioning/revocation is
  out of scope.

### What it does NOT protect against (current phase)

The floor (TAMP backup registers) survives a system reset and a reflash, but the
TAMP backup domain is only retained through a full power-off when **VBAT is
supplied**. On the open Nucleo without a VBAT coin cell, a true power-loss /
VBAT-pull resets the floor to 0; the `COLD_WINDOW` scan then admits an old
version ≤ 1024 again (fail-open, logged as `rollback floor cold (0)`). Chip
replacement is likewise out of scope. This is the **VBAT-trust assumption**.

**Closing the gap (deferred):** swap the `MonotonicCounter` impl
(`BackupFloorCounter` in `boot/src/antirollback.rs`) for an OTP/BSEC monotonic fuse
counter — durable vs a physical attacker, but gated on the irreversible
`secure_boot` OTP close, out of scope on the open dev board. The OTP counter is
a finite budget (~32 states on the N6 BootROM analogue); a production policy must
cap/partition version bumps to avoid bricking upgrades.

### Building with anti-rollback enabled

Enable BOTH gates so the offline blob and the kernel agree:

```bash
# offline: bind the version into the measurement
export UMBRA_VERSION_BIND=1 UMBRA_AUTHOR_ID=1 UMBRA_ENCLAVE_VERSION=2
# firmware: build the N657 boot crate with the `enclave_version_bind` feature
#   (add it to the boot crate's enabled features / BOOT_FEATURES)
```

The on-hardware proof is `tools/test_enclave_rollback_negative.sh` (accept v2,
then refuse a re-presented v1 while the board stays powered). The firmware
`version_tag` byte layout is kept in lock-step with the Python helper by
`tools/test_enclave_version_guard.py`.

## Inter-enclave overlay switch

Running a single enclave larger than the resident code-block budget, or running two
enclaves that time-share the same on-chip window, both need eviction. On N657 the
enclave executes unprivileged with `PRIVDEFENA=1`, so the MPU raises a precise,
synchronous `MemManage` fault on any data or instruction access outside its current
regions — a data trap the memory firewall does not give. That trap is what makes
eviction safe: a whole enclave's code/data window can be evicted to an SRAM backing
over DMA, MPU-fenced, and restored on re-entry without silently corrupting a stray
access. A transparent cache that relocates individual blocks is not feasible (the
Cortex-M55 has no MMU and the enclave's branches are position-fixed), so the switch
is coarse-grained: it swaps the whole window between two enclaves that keep their own
fixed layout. See the [ESS model](../architecture/ess-model.md#eviction-feasibility)
and [ADR 011](../decisions/011-enclave-eviction-feasibility.md) for the full
trap/cache-model analysis.

### Speculative window switch

The SysTick overlay switch is non-blocking by default. Only the 2 KB chunk containing
the incoming enclave's resume PC is moved synchronously (evict + restore); the enclave
resumes immediately on an MPU region-5 reveal rotated to that chunk, while HPDMA1
channel 2 carries the remaining chunk pairs in the background (the TC IRQ chains the
transfers; PendSV invalidates caches and grows the reveal while it stays contiguous).
Correctness never depends on the speculation winning: if the enclave reaches a
still-hidden chunk, the MemManage handler recovers it.

**Hot-chunk prefetch.** An enclave's working set is a code chunk plus a data chunk
(its `.data`/`.bss` live at the window tail, far from the resume PC), and it touches
that data within a few instructions of every resume. A single contiguous reveal cannot
cover both cheaply, so the switch pre-restores *two* chunks synchronously — the resume-PC
chunk (revealed via region 5) and the enclave's learned hot data chunk (revealed via a
dedicated MPU region). The hot chunk is learned from the address of the first fault each
enclave takes (measured to be static per enclave) and applied on its next switch.

**Non-destructive miss recovery.** When the enclave does reach a hidden chunk, the fault
handler does not abandon the whole speculation: it synchronously restores and reveals
just the gap up to the faulting chunk, then *resumes* the background chain for the chunks
beyond it — so those can still complete asynchronously and land as hits within the same
quantum. It falls back to a full synchronous drain only for the wrapped-chunk case.

This is HW-verified: the background chain completes under a live enclave (a hit, no
drain) for a locality-compact working set; an enclave whose hot data sits at the very
tail of the window degrades gracefully toward synchronous. The `overlay_sync_switch`
feature (`UMBRA_OVERLAY_SYNC_SWITCH=1`) forces the old fully-synchronous switch for
bisection.

## State continuity (execution state)

The version-bind floor above protects the enclave *binary* — it refuses an older
signed image. A separate control protects the enclave's *runtime state*: after a
warm reset it refuses to resume a stale or tampered snapshot of the enclave's
mutable memory (stack, data, saved registers), again against a software /
warm-reset attacker.

Freshness lives **entirely in the trusted TAMP anchor as a keyed root** over the
whole logical state; external flash is untrusted and holds only ciphertext:

- The anchor stores `{generation, root, per-sector parity}`, where
  `root = HMAC(MASTER_KEY, enclave_id ‖ state_format_version ‖ generation ‖ H(sector_0) ‖ … ‖ H(sector_15))`
  truncated to 128 bits and `H(sector_i)` is a plain SHA-256 of that sector's
  committed ciphertext. Because the keyed root sits in Secure-write-only backup
  registers, a stale state recomputes a *different* root and cannot be forged.
  `state_format_version` is an author-owned tag for the snapshot layout (bumped only
  when the layout changes, **not** the code version), so an incompatible layout fails
  closed instead of being deserialized — the version-bind floor stays a separate
  control (see [ADR 010](../decisions/010-state-continuity-commit-reconciliation.md)).
- A checkpoint stages dirty sectors into their A/B staging slots, recomputes the
  root over the new committed state, and commits one new anchor. Restore
  recomputes the root over the committed slots and compares it constant-time — a
  match resumes; any mismatch (rollback, replay of a whole old-but-coherent
  snapshot, tamper, mix-and-match of slots) is a hard reject.
- The anchor spans several registers, so it is **double-buffered** with a trailing
  generation-echo written last; a reset mid-commit is detected and the previous
  good copy is used. The two copies live past the version-bind floor in the
  backup-register file.

The threat-model boundary matches the floor: a cold power-off (no VBAT) zeroes the
anchor, so restore then fails **open** and trusts the current flash as a new
baseline — cold boot is physical power-off, out of scope here, and the
`PWR_SECCFGR.SEC5` fix closes the software cold-equivalent path. See
[ADR 009](../decisions/009-state-continuity-power-session-boundary.md) and
[ADR 010](../decisions/010-state-continuity-commit-reconciliation.md).

**Status.** The checkpoint/restore logic and the double-buffered anchor are
implemented and host-tested (`kernel::key_storage_server::{state_root,
state_checkpoint}` and `drivers::state_anchor`). Wiring the flash side to real
XSPI2 (the raw 1-1-1 write path for the state region, outside the MCE2 enclave
window) and hooking checkpoint/restore into the enclave yield/resume path is
hardware bring-up work, tracked separately.
